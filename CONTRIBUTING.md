# Contributing to Linux World

Thank you for helping improve Linux World. Contributions that strengthen accuracy, safety, clarity, accessibility, and practical value are welcome.

## Before contributing

Before opening an issue or pull request:

1. Read the [Code of Conduct](CODE_OF_CONDUCT.md).
2. Read the [License](LICENSE).
3. Search existing issues and pull requests.
4. Confirm that the proposed change fits the repository's Linux focus.
5. Test every technical instruction in a safe, disposable environment.

## Good contributions

Useful contributions include:

- Correcting technical inaccuracies
- Fixing spelling, grammar, formatting, or broken links
- Clarifying unclear explanations
- Adding verified expected output
- Reporting distribution-specific differences
- Improving accessibility
- Adding safety warnings
- Reporting outdated commands or procedures
- Proposing a new lab, troubleshooting case, or project through an issue

Large unsolicited rewrites may be closed. Open an issue before starting a substantial contribution.

## Issues

Use an issue for documentation errors, enhancement proposals, broken links, or questions about repository content.

A useful issue includes:

- A clear title
- The affected file or section
- The Linux distribution and version, when relevant
- The current behavior
- The expected behavior
- Commands used and sanitized output
- Reproduction steps
- Screenshots or logs when they materially help

Do not include passwords, tokens, private keys, personal information, internal hostnames, private IP addresses, or confidential logs.

Security vulnerabilities must not be reported in public issues. Follow [SECURITY.md](SECURITY.md).

## Pull requests

Pull requests should:

- Address one focused change
- Link to a related issue when one exists
- Explain what changed and why
- Identify the distributions and versions tested
- Include expected output and verification steps for technical changes
- Preserve the existing writing and formatting style
- Avoid unrelated formatting changes
- Avoid generated filler, copied material, and unverifiable claims
- Contain no secrets, personal data, or confidential information

## Technical documentation standard

New or substantially revised technical material should include, where relevant:

- Purpose and learning objectives
- Prerequisites
- Concepts explained from first principles
- Commands and options explained
- Files and directories involved
- Expected output
- Verification steps
- Common errors and troubleshooting
- Security and production considerations
- Safe cleanup or rollback instructions
- References to authoritative upstream documentation

## Original work and third-party material

Contributors must submit only work they have the right to contribute.

Do not submit:

- Copied articles, books, courses, documentation, or repository content
- Material produced under incompatible terms
- Confidential employer or client information
- Proprietary code or internal procedures
- Images, diagrams, or screenshots without permission
- Content that infringes copyright, trademark, privacy, or other rights

Short quotations must be necessary, properly attributed, and legally permitted. Prefer paraphrasing and linking to authoritative sources.

Submission does not guarantee acceptance. Maintainers may request changes, edit accepted material for consistency, close inactive submissions, or decline contributions that do not fit the repository.

Accepted contributors may be recognized through Git history, release notes, or contributor listings. Attribution does not change repository ownership or licensing.

# 01. Project Title

## Enterprise High-Availability Linux Infrastructure

You are responsible for an application currently running on a single Linux server.

The existing architecture is:

```text
                 USERS
                   │
                   ▼
               ┌────────┐
               │ WEB01  │
               │ Nginx  │
               └────────┘
```

There is an obvious problem.

If `WEB01` disappears:

```text
WEB01 failure
     │
     ▼
Application failure
     │
     ▼
User outage
```

Your job is to replace that architecture with this:

```text
                           CLIENT
                              │
                              ▼
                    192.168.56.100
                     SERVICE VIP
                              │
                   ┌──────────┴──────────┐
                   │                     │
                 LB01                  LB02
             HAProxy + VRRP        HAProxy + VRRP
                   │                     │
                   └──────────┬──────────┘
                              │
                        HAProxy pool
                              │
                  ┌───────────┴───────────┐
                  │                       │
                WEB01                   WEB02
                Nginx                   Nginx
                  │                       │
                  └───────────┬───────────┘
                              │
                         APPLICATION

                              │
                              ▼
                            MON01
                     Prometheus / Metrics

ADMIN01
   │
   ├── administration
   ├── validation
   ├── load testing
   ├── failure testing
   └── evidence collection
```

The finished platform must tolerate selected single-component failures while preserving application service.

But you must also know where it **cannot** survive.

That distinction is one of the central lessons of the project.

# 02. Project Scenario

Your company operates an internal business application.

It has become important enough that management no longer accepts a single-server deployment.

The requirements given to the infrastructure team are:

```text
REQ-01  Users must access one stable service address.

REQ-02  Loss of one web server must not cause a complete outage.

REQ-03  Loss of the active load balancer must trigger automatic failover.

REQ-04  Failed backends must automatically leave traffic rotation.

REQ-05  Recovered backends must return automatically after proving health.

REQ-06  Operators must know when redundancy has degraded.

REQ-07  Infrastructure health must be monitored.

REQ-08  Local process failures should recover automatically where safe.

REQ-09  Planned maintenance should not require a full application outage.

REQ-10  Configuration changes must be validated before activation.

REQ-11  Recovery behavior must be measured rather than assumed.

REQ-12  The architecture and operational limitations must be documented.
```

These requirements are important because **high availability is not a product you install**.

It is a property produced by architecture and operations.

Installing Keepalived does not make an application highly available.

Installing two web servers does not make an application highly available.

Installing Prometheus does not make an application reliable.

You have to prove that the entire service path behaves correctly during failure.

## ADR-002 — Active/passive load-balancer entry point

The backend tier will be active/active:

```text
WEB01 + WEB02
```

The VIP will be active/passive:

```text
LB01 OR LB02
```

Why?

Because a single floating address provides a straightforward way to teach Linux network failover.

---

## ADR-003 — Health checks must be layered

You will use different checks for different questions.

Backend health asks:

> Can this application backend serve traffic?

Load-balancer health asks:

> Can this load balancer accept traffic?

Service health asks:

> Can a client successfully use the service?

Those are not interchangeable.

# 10. Failure-Domain Design

Before installing anything, create:

```bash
nano ~/enterprise-ha-linux/FAILURE-DOMAINS.md
```

Document this matrix:

| Failure              | Expected behavior                                  |
| -------------------- | -------------------------------------------------- |
| WEB01 Nginx fails    | WEB02 serves traffic                               |
| WEB01 VM fails       | WEB02 serves traffic                               |
| WEB02 fails          | WEB01 serves traffic                               |
| Both backends fail   | Application unavailable                            |
| Standby LB fails     | Application remains available; redundancy degraded |
| Active HAProxy fails | VIP moves to healthy peer                          |
| Active LB VM fails   | VIP moves to peer                                  |
| Both LBs fail        | Application unavailable                            |
| MON01 fails          | Application continues; observability degraded      |
| ADMIN01 fails        | Application continues                              |
| VM host fails        | Entire lab may fail                                |

That last line is important.

Running six VMs on one laptop does **not** create six independent physical failure domains.

Your hypervisor host remains a common dependency.

# Phase 16 — Configure HAProxy

Back up:

```bash
sudo cp /etc/haproxy/haproxy.cfg \
    /etc/haproxy/haproxy.cfg.pre-veriqta
```

Create:

```bash
sudo tee /etc/haproxy/haproxy.cfg >/dev/null <<'EOF'
global
    log /dev/log local0
    log /dev/log local1 notice

    chroot /var/lib/haproxy

    user haproxy
    group haproxy

    daemon

    stats socket /run/haproxy/admin.sock mode 660 level admin
    stats timeout 30s

defaults
    log global
    mode http

    option httplog
    option dontlognull

    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend veriqta_frontend
    bind *:80
    default_backend veriqta_backends

backend veriqta_backends
    balance roundrobin

    option httpchk
    http-check send meth GET uri /health
    http-check expect status 200

    default-server inter 2s fall 3 rise 2

    server web01 192.168.56.31:80 check
    server web02 192.168.56.32:80 check

frontend lb_local_health
    bind 127.0.0.1:8404
    http-request return status 200 content-type text/plain string "OK\n"
EOF
```

The UNIX Runtime API socket is intentionally local. HAProxy documents both UNIX and network sockets, and warns that exposing a Runtime API network listener can make it available to unauthorized clients unless it is appropriately protected. ([HAProxy Technologies][1])

# Phase 17 — Understand the Health Model

HAProxy checks:

```text
WEB01 /health
WEB02 /health
```

Every:

```text
2 seconds
```

with:

```text
fall 3
```

and:

```text
rise 2
```

Conceptually:

```text
WEB01 healthy
   │
three failed checks
   ▼
WEB01 DOWN
   │
removed from rotation
   │
two successful checks
   ▼
WEB01 UP
```

This avoids reacting to one isolated failed request.

# Phase 18 — Why the Load Balancer Has a Separate Health Endpoint

Keepalived should answer:

> Is HAProxy on this machine capable of accepting client traffic?

It should not answer:

> Are the application backends healthy?

Imagine both backends fail.

HAProxy might return:

```text
503
```

Moving the VIP from LB01 to LB02 would accomplish nothing because LB02 uses the same failed backend pool.

Therefore:

```text
127.0.0.1:8404
```

provides a local HAProxy health signal independent of the backend pool.

This distinction prevents an application-tier failure from unnecessarily becoming a load-balancer failover event.

# 16. Prove Backend Failover Before VIP Failover

On `admin01`:

```bash
while true; do
    printf '%s ' "$(date -u '+%H:%M:%S')"
    curl -s --max-time 2 http://192.168.56.20/ |
        grep -o 'WEB0[12]' || echo FAILED
    sleep 1
done
```

Now stop WEB01:

```bash
sudo systemctl stop nginx
```

Observe.

After the configured health threshold, HAProxy should stop directing requests to WEB01.

Check:

```bash
echo "show stat" |
sudo socat stdio /run/haproxy/admin.sock |
grep web01
```

Restore:

```bash
sudo systemctl start nginx
```

After the recovery threshold, WEB01 should rejoin.

You have now proved:

```text
backend failure
      ↓
failure detected
      ↓
backend isolated
      ↓
service continues
      ↓
backend repaired
      ↓
health re-established
      ↓
backend restored
```

## Phase 38 — Build `cluster-health.sh`

On ADMIN01:

```bash
nano ~/enterprise-ha-linux/scripts/cluster-health.sh
```

Create:

```bash
#!/usr/bin/env bash

set -u

VIP="192.168.56.100"

declare -A NODES=(
    [lb01]="192.168.56.20"
    [lb02]="192.168.56.21"
    [web01]="192.168.56.31"
    [web02]="192.168.56.32"
    [mon01]="192.168.56.40"
)

failed=0

echo "=============================================="
echo " VERIQTA ENTERPRISE HA HEALTH CHECK"
echo " $(date -u '+%Y-%m-%dT%H:%M:%SZ')"
echo "=============================================="

echo
echo "[NODE REACHABILITY]"

for name in "${!NODES[@]}"; do
    ip="${NODES[$name]}"

    if ping -c 1 -W 1 "$ip" >/dev/null 2>&1; then
        printf 'PASS %-8s %s\n' "$name" "$ip"
    else
        printf 'FAIL %-8s %s\n' "$name" "$ip"
        failed=1
    fi
done

echo
echo "[SERVICE VIP]"

if response="$(curl -fsS --max-time 2 "http://${VIP}/" 2>/dev/null)"; then
    echo "PASS VIP application reachable"

    backend="$(printf '%s\n' "$response" |
        sed -n 's/.*Backend: \(WEB0[12]\).*/\1/p')"

    echo "RESPONDING_BACKEND=${backend:-UNKNOWN}"
else
    echo "FAIL VIP application unavailable"
    failed=1
fi

echo
echo "=============================================="

if [[ "$failed" -eq 0 ]]; then
    echo "BASIC AVAILABILITY CHECK: PASS"
    exit 0
fi

echo "BASIC AVAILABILITY CHECK: FAIL"
exit 1
```

Then:

chmod +x ~/enterprise-ha-linux/scripts/cluster-health.sh
```

```

# 41. Interview Preparation

Every question below is supported by something you have already built or investigated.

### What is the difference between redundancy and high availability?

Redundancy means additional components exist.

High availability requires those components, their failover mechanisms and their capacity to preserve the required service during defined failures.

---

### Why are two web servers not automatically highly available?

Because you also need:

```text
traffic distribution
health detection
failure isolation
surviving capacity
network availability
```

If clients still connect directly to one server, the second server may provide no availability benefit.

---

### Why use both HAProxy and Keepalived?

HAProxy decides:

```text
Which healthy backend should receive this request?
```

Keepalived/VRRP decides:

```text
Which load balancer should own the service IP?
```

Different failure domains require different mechanisms.

---

### Why did you not make backend failure cause VIP failover?

Because moving the VIP cannot repair a backend-pool failure shared by both load balancers.

You separated:

```text
load-balancer health
```

from:

```text
application backend health.
```

---

### What is the purpose of `fall` and `rise`?

They introduce health-state thresholds.

`fall` determines how many consecutive failures are required before declaring a server down.

`rise` determines how many successful checks are required before declaring it healthy again.

---

### What is a false-positive health check?

A check says the service is healthy even though it cannot perform its required function.

A static `/health` file can produce this problem if critical application dependencies have failed.

---

### Can a health check also be too deep?

Yes.

If the health endpoint depends on every downstream service, failure of a noncritical dependency can remove otherwise useful application capacity.

---

### What is degraded availability?

In this project:

```text
WEB01 DOWN
WEB02 UP
```

may mean:

```text
service available
redundancy degraded.
```

That condition deserves monitoring even though users may not yet experience an outage.

---

### Why is the Runtime API socket security-sensitive?

It can provide operational control over the running load balancer, including runtime server-state changes. HAProxy supports access levels for its Runtime API sockets, and UNIX-socket permissions can restrict local access. ([HAProxy Technologies][1])

---

### Why isn't syntax validation enough?

A configuration can be syntactically valid while being logically wrong.

Your wrong-backend experiment proved that.

---

### Why test one-backend capacity?

Because high availability requires the surviving infrastructure to carry required workload.

Two servers at near-full combined utilization may not provide meaningful N+1 capacity.

---

### What is the difference between failover and failback?

Failover transfers responsibility away from a failed component.

Failback returns responsibility to a preferred recovered component.

---

### Why can automatic failback be undesirable?

Because service is already operating.

Moving it again introduces another transition and potentially another disruption.

---

### Why use client-side testing during failover?

Because infrastructure state alone doesn't tell you what the user experienced.

Your client probe measures actual successful and failed requests.

---

### What happens if MON01 fails?

Application traffic can continue because MON01 is outside the application data path.

However, observability is degraded.

---

### What happens if the physical laptop running all VMs fails?

The entire lab fails.

The VMs share a physical failure domain.

---

### Does this architecture eliminate all SPOFs?

No.

No honest Senior project should make that claim.

This architecture protects against **defined component failures**.

The local hypervisor, physical network, power source and other shared dependencies can remain common failure domains.

# 44. Project Reflection — With Answer Guidance

These questions are part of the project rather than unrelated exam trivia.

1. **Why are WEB01 and WEB02 active/active?** Because both normally serve application traffic.

2. **Why are LB01 and LB02 active/passive at the VIP layer?** Because only one node normally owns the floating client address.

3. **What failure does HAProxy solve?** Backend selection and isolation of unhealthy backend servers.

4. **What failure does Keepalived solve?** Loss of the load balancer currently owning the service VIP.

5. **Why doesn't Keepalived replace HAProxy?** VIP ownership and application traffic distribution are different responsibilities.

6. **Why doesn't HAProxy alone remove the LB SPOF?** Clients would still depend on whichever HAProxy endpoint they were configured to use.

7. **Why did you validate backend failover before configuring VRRP?** To isolate troubleshooting layers and avoid debugging the entire architecture simultaneously.

8. **Why does the health script test local HAProxy rather than the backend pool?** Because backend failure should not unnecessarily trigger LB failover.

9. **What happens if both backends fail?** The application becomes unavailable even though the load-balancing layer may remain healthy.

10. **Why does that not automatically mean the VIP should move?** The peer LB uses the same failed backends, so VIP movement does not solve the failure.

11. **Why are `fall` and `rise` useful?** They reduce health-state flapping caused by transient checks.

12. **Why is `/health` potentially insufficient in a real application?** A static endpoint may not reflect critical dependency health.

13. **Why shouldn't a health endpoint blindly check every dependency?** Noncritical dependency failure could unnecessarily remove all application capacity.

14. **What does `priority 150` versus `100` accomplish?** It makes LB01 preferred while both are healthy.

15. **Why was the health-script weight chosen large enough to cross the peer's priority?** So unhealthy LB01 actually becomes less preferred than healthy LB02.

16. **What happens if VRRP communication is lost?** Peer coordination can fail and duplicate VIP ownership may occur.

17. **Why is duplicate VIP ownership dangerous?** Network neighbors may receive inconsistent information about where the service IP resides.

18. **Why observe packets during troubleshooting?** Packet capture proves whether expected network traffic actually exists.

19. **What does a successful `systemctl status nginx` prove?** Primarily that systemd considers the service process active—not that the application is functionally healthy.

20. **What does Node Exporter prove?** Host-level metrics and availability, not end-to-end application correctness.

21. **Why monitor the VIP separately?** It represents the endpoint users actually consume.

22. **Why monitor healthy-backend count?** Service can remain available after redundancy has already been lost.

23. **Why perform load testing after removing one backend?** To test whether surviving capacity is sufficient.

24. **What is N+1 capacity?** Enough spare capacity to continue meeting requirements after loss of one required component.

25. **Why is a successful HAProxy configuration check insufficient after a change?** It proves syntax validity, not functional correctness.

26. **Why perform post-change validation?** To prove the desired service behavior remains intact.

27. **Why have a rollback plan before the change?** Recovery is easier and faster when the known-good state and restoration procedure are predetermined.

28. **Why change the redundant/standby component first?** It limits blast radius and lets you observe the change before touching the active service path.

29. **Why collect UTC timestamps?** They allow consistent cross-system event correlation.

30. **Why record client-side failures?** They quantify actual user-visible impact.

31. **Why doesn't one successful `curl` prove HA?** It demonstrates one successful request under one condition, not resilience.

32. **Why deliberately break the system?** Because failure assumptions should be tested rather than trusted.

33. **Why reboot nodes as well as stopping services?** Machine loss exercises different detection and recovery mechanisms.

34. **Why test a full restart?** To verify boot-time service enablement and dependency recovery.

35. **Why keep an incident report?** It converts raw troubleshooting into an auditable explanation of impact, cause, recovery and prevention.

36. **Why document limitations?** Because engineering claims must match what the architecture actually protects against.

37. **What major SPOF remains in a laptop lab?** The physical host/hypervisor and potentially its network/storage/power.

38. **Would this exact design automatically qualify as production HA?** No. Production requirements depend on failure domains, traffic, security, availability objectives, physical infrastructure, capacity and operational requirements.

39. **What did the project automate?** Backend health handling, VIP election/failover, local process supervision where configured, monitoring, health checks and selected operational tests.

40. **What still requires an engineer?** Architecture decisions, unusual incidents, capacity decisions, unsafe or ambiguous recovery, root-cause analysis, changes and improvements.

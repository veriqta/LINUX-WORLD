# 02. Project Scenario

You are the senior Linux infrastructure engineer responsible for an internal business application called the **VERIQTA Operations Platform**.

The existing environment has grown organically.

It currently consists of one Linux server:

```text
users
  │
  ▼
web01
  │
  ├── Nginx
  └── Application
```

This creates an obvious single point of failure.

If `web01` fails:

```text
service unavailable
```

Management has established a new availability requirement.

The platform must tolerate the loss of:

* one application server;
* one load balancer;
* one application process;
* one HAProxy process;
* selected network paths;
* selected service failures.

You are asked to redesign the service.

However, there is an important constraint:

> Buying more servers is not the same as building high availability.

For example:

```text
                    CLIENT
                       │
                       ▼
                      LB01
                     /    \
                    /      \
                   ▼        ▼
                WEB01      WEB02
```

The backend tier is redundant.

But:

```text
LB01 fails
   ↓
entire platform fails
```

You have simply moved the single point of failure.

Your architecture must therefore examine the **whole request path**.

# Load-Balancer Control Plane

```text
             VRRP
       advertisements
            │
     ┌──────┴──────┐
     │             │
     ▼             ▼
   LB01 ◄────────► LB02
    │               │
priority           priority
  150                100
```

Normal state:

```text
LB01 = VIP owner
LB02 = standby
```

Failure state:

```text
LB01 unhealthy
      │
      ▼
LB02 becomes VIP owner
```

# Monitoring Path

```text
                     MON01
                       │
       ┌───────────────┼───────────────┐
       │               │               │
       ▼               ▼               ▼
      LB01            LB02           WEB01
       │                               │
       └───────────────┬───────────────┘
                       ▼
                     WEB02
```

You will monitor both:

```text
SERVICE AVAILABILITY
```

and:

```text
REDUNDANCY HEALTH
```

These are not the same.

Suppose:

```text
LB01 = healthy
LB02 = dead
VIP = healthy
```

Users may still receive successful responses.

Therefore:

```text
SERVICE = AVAILABLE
REDUNDANCY = DEGRADED
```

That distinction is a major theme of this project.

# Failure Domains

Create a failure-domain table before implementation.

| Failure                           | Expected Service Effect                                |
| --------------------------------- | ------------------------------------------------------ |
| `web01` fails                     | Service remains available through `web02`              |
| `web02` fails                     | Service remains available through `web01`              |
| Both web nodes fail               | Service unavailable                                    |
| `lb01` fails                      | VIP transfers to `lb02`                                |
| `lb02` fails while passive        | Service remains available, redundancy degraded         |
| HAProxy fails on active LB        | VIP should transfer if service tracking is functioning |
| Keepalived fails on active LB     | VIP should transfer                                    |
| Monitoring fails                  | Service remains available, visibility degraded         |
| `admin01` fails                   | Production traffic unaffected                          |
| Network shared by all nodes fails | Platform may become unavailable                        |

That last line matters.

You have not eliminated every SPOF simply because you created multiple VMs.

# Configure HAProxy

Create:

```bash
sudo nano /etc/haproxy/haproxy.cfg
```

Use:

```text
global
    log /dev/log local0
    log /dev/log local1 notice

    chroot /var/lib/haproxy
    stats socket /run/haproxy/admin.sock mode 660 level admin
    stats timeout 30s

    user haproxy
    group haproxy
    daemon

defaults
    log global
    mode http
    option httplog
    option dontlognull

    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend veriqta_http
    bind *:80
    default_backend veriqta_backends

backend veriqta_backends
    balance roundrobin

    option httpchk GET /health
    http-check expect status 200

    default-server inter 2s fall 3 rise 2

    server web01 192.168.56.31:80 check
    server web02 192.168.56.32:80 check
```

# Understand the Health Timing

This matters.

```text
inter 2s
```

means checks approximately every two seconds.

```text
fall 3
```

requires consecutive failed checks before the backend is considered down.

Conceptually:

```text
2 seconds × 3 failures
≈ 6 seconds
```

before detection, although real observed timing can differ.

`rise 2` requires successful checks before the server is restored to service.

Do not promise an exact six-second recovery time from configuration alone.

Measure it.

# VRRP

The two load balancers participate in an election.

# Important Health-Check Design Decision

This check traverses:

```text
local HAProxy
    ↓
backend selection
    ↓
backend HTTP service
```

Therefore it answers:

> Can this load balancer currently serve an application request?

That is deeper than checking only the HAProxy process.

But it creates a trade-off.

If **all backends fail**, both load balancers may fail this check.

That can cause unnecessary VIP movement even though neither LB is the actual problem.

This is a senior-level design decision.

You have at least two strategies:

### Strategy A — LB-local health

Check only whether HAProxy's local frontend/runtime is healthy.

Advantage:

```text
backend failure does not trigger LB failover
```

Disadvantage:

```text
less end-to-end coverage
```

### Strategy B — End-to-end health

Check whether HAProxy can return a valid backend response.

Advantage:

```text
deeper service validation
```

Disadvantage:

```text
shared backend failure can destabilize the LB election
```

For this project, begin with the end-to-end check so you can observe this failure mode.

Later you will redesign it.

That redesign is part of the project.

# Phase 9 — Build an Infrastructure Health Script

Use:

```bash
#!/usr/bin/env bash

set -u

VIP="192.168.56.100"
LB01="192.168.56.20"
LB02="192.168.56.21"
WEB01="192.168.56.31"
WEB02="192.168.56.32"

FAILURES=0

check_http() {
    local name="$1"
    local url="$2"

    local code

    code="$(
        curl \
            --silent \
            --output /dev/null \
            --write-out '%{http_code}' \
            --max-time 3 \
            "$url" 2>/dev/null || true
    )"

    if [[ "$code" == "200" ]]; then
        printf '%-12s HEALTHY  HTTP %s\n' "$name" "$code"
    else
        printf '%-12s FAILED   HTTP %s\n' "$name" "${code:-000}"
        ((FAILURES+=1))
    fi
}

echo "VERIQTA HA PLATFORM HEALTH"
echo "UTC: $(date -u '+%Y-%m-%dT%H:%M:%SZ')"
echo

check_http "VIP"    "http://${VIP}/"
check_http "LB01"   "http://${LB01}/"
check_http "LB02"   "http://${LB02}/"
check_http "WEB01"  "http://${WEB01}/health"
check_http "WEB02"  "http://${WEB02}/health"

echo

if (( FAILURES == 0 )); then
    echo "Overall: HEALTHY"
    exit 0
fi

echo "Overall: DEGRADED OR FAILED"
exit 1
```

```bash
            "$timestamp" \
            "${backend:-unknown}"
    else
        printf '%s FAILURE curl_rc=%d\n' \
            "$timestamp" \
            "$rc"
    fi

    sleep "$INTERVAL"
done
```

# Automated Recovery Layers

Your platform now has several recovery mechanisms:

```text
LEVEL 1
systemd restarts a failed process

LEVEL 2
HAProxy removes an unhealthy backend

LEVEL 3
Keepalived moves the VIP away from an unhealthy LB

LEVEL 4
Operator performs infrastructure recovery
```

Document these explicitly.

```text
Nginx crashes
   ↓
systemd attempts recovery
   ↓
```

Load balancer:

```text

   ↓

   ↓
peer becomes preferred
   ↓
VIP transfers
   ↓
monitoring alerts
   ↓
operator investigates failed LB
```

That is layered recovery.

# 23. Interview Preparation

### What is high availability?

The design and operation of systems to maintain an acceptable level of service despite expected component failures.

### Is redundancy the same as HA?

No.

Redundancy provides alternatives.

High availability requires those alternatives to be detected, selected, transitioned to, monitored, and validated correctly.

### What is a single point of failure?

A component whose failure can independently make the required service unavailable.

### What is a failure domain?

A set of components that can fail together because they share a dependency or fault boundary.

### Why are two web servers insufficient for full HA?

The load balancer, network, database, DNS, storage, power, or other shared dependencies may still be single points of failure.

### What is active/active?

Multiple nodes simultaneously serve production workload.

### What is active/passive?

One node normally provides a role while another waits to assume it after failure.

### What is HAProxy doing here?

Distributing requests across healthy application backends and removing failed backends from rotation.

### What is Keepalived doing?

Coordinating service endpoint ownership between redundant load balancers.

### What is VRRP?

A protocol used to coordinate ownership of a virtual routing/service address between participating nodes.

### Why use a VIP?

Clients need a stable service endpoint even when the machine serving that endpoint changes.

### What happens when `web01` fails?

HAProxy's health checks should eventually mark it unavailable and route new traffic to `web02`.

### Does an existing TCP connection automatically migrate from a failed backend?

No.

That is an important reason not to equate HA with zero interruption.

### What does `fall 3` mean?

A backend must fail the configured number of consecutive checks before being considered unavailable.

### What does `rise 2` mean?

A failed backend must pass the configured number of checks before being considered available again.

### Why not check only `systemctl is-active`?

A process can be active while its service is unusable.

### Can a health check be too deep?

Yes.

If an LB ownership check depends on shared downstream components, downstream failure can incorrectly trigger LB failover.

### What is a false-positive health check?

A health check reports healthy while the real user-facing function is broken.

### What is a false-negative health check?

The health check reports failure even though the component could still correctly provide the required service.

### What is failover?

Transitioning service responsibility to a redundant component after failure.

### What is failback?

Returning responsibility to a previously failed/recovered preferred component.

### Why can automatic failback be risky?

An unstable recovered node can cause repeated ownership transitions or additional interruption.

### What is flapping?

Repeated state transitions between healthy/unhealthy or active/standby conditions.

### Why use unicast VRRP in this lab?

It can be easier to operate in virtual networks where multicast behavior is limited or unreliable.

### Why does VRRP need firewall consideration?

VRRP uses IP protocol 112 rather than a normal TCP/UDP service port.

### What happens if VRRP peers cannot communicate?

Each side may make incorrect ownership decisions, potentially producing duplicate VIP ownership.

### What is degraded redundancy?

The service is currently available but has lost some ability to survive another failure.

### Why should degraded redundancy alert?

Because the next component failure may become a service outage.

### What is graceful degradation?

Maintaining reduced but useful service rather than total failure.

### Why drain a backend before maintenance?

To stop new traffic reaching it while allowing controlled removal from production.

### Reload versus restart?

A reload generally attempts to apply configuration with less disruption, whereas restart stops and starts the service process. Exact semantics depend on the service.

### Why validate configuration first?

A syntactically broken configuration should never be allowed to replace a currently functioning runtime configuration.

### Why test firewall failures?

A service may be healthy locally while unreachable across the required network path.

### Why test slow backends?

Many production failures are degradation rather than complete failure.

### What is automated recovery?

A defined mechanism that detects a failure condition and performs a bounded corrective action without requiring immediate human intervention.

### Why can automated recovery be dangerous?

Incorrect detection or unbounded remediation can amplify failures.

### What is a restart storm?

A repeatedly crashing service is automatically restarted continuously, consuming resources and obscuring the underlying problem.

### Why use systemd start-rate limiting?

To bound repeated restart behavior.

### What should monitoring distinguish?

At minimum:

```text
service availability
component health
redundancy health
capacity
performance
```

### Why isn't monitoring a runtime dependency?

The application should ideally continue serving traffic if the monitoring system itself fails.

### What is observability?

The ability to understand internal system behavior using externally available signals such as metrics, logs, traces, events, and state.

### Why is time synchronization important?

Cross-node troubleshooting and incident timelines require comparable timestamps.

### What is RTO?

Recovery Time Objective: the target time within which service or functionality should be restored after disruption.

### Does HA eliminate disaster recovery?

No.

HA addresses certain failures while DR addresses recovery from larger loss scenarios.

### Does this architecture make the database highly available?

No.

There is no database tier in this project.

Adding a single database behind redundant web servers would create another SPOF.

### Is the monitoring server a SPOF?

For observability, yes.

It is not intended to be a runtime dependency of the application in this lab.

### Is the network still a failure domain?

Yes.

The lab does not create redundant physical switches, NICs, routers, power domains, hypervisors, or data centers.

### Is this production-ready?

It is a production-style engineering lab.

A real enterprise deployment must additionally address physical/network failure domains, secrets, PKI/TLS, DNS, patching, centralized logs, configuration management, backups, application state, database HA, capacity, multi-zone/site design, organizational controls, and many environment-specific requirements.

# Senior Completion Standard

This project is **not complete** because:

```bash
curl http://192.168.56.100
```

returns `200`.

It is complete when you can explain and demonstrate the entire system:

```text
                         CLIENT
                            │
                            ▼
                      SERVICE VIP
                            │
                 ┌──────────┴──────────┐
                 │                     │
                 ▼                     ▼
               LB01                  LB02
                 │                     │
                 └──────────┬──────────┘
                            │
                         HAProxy
                            │
                 ┌──────────┴──────────┐
                 │                     │
                 ▼                     ▼
               WEB01                 WEB02
                 │                     │
                 └──────────┬──────────┘
                            │
                            ▼
                       APPLICATION
```

and then explain what happens when **every arrow and every box fails individually**.

Your operational reasoning should be:

```text
What service are we protecting?
          ↓
What availability does it require?
          ↓
What components deliver that service?
          ↓
What are their failure domains?
          ↓
Where are the single points of failure?
          ↓
How do we detect each failure?
          ↓
Which failures can be handled automatically?
          ↓
Who owns each recovery action?
          ↓
What happens during partial failure?
          ↓
How do we know redundancy is degraded?
          ↓
How do we maintain the platform safely?
          ↓
How do we measure failover?
          ↓
How do we prove recovery?
          ↓
What happens if automation itself fails?
          ↓
What risks remain?
```

And the most important distinction to carry forward into the rest of the **Senior Linux World** projects is:

> **Redundancy means you have another component. High availability means the system can detect failure, transfer responsibility, continue providing an acceptable service, recover safely, and prove that the protection still works.**

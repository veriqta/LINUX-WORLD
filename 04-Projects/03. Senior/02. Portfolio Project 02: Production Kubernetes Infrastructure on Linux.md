# Portfolio Project 02 — Production Kubernetes Infrastructure on Linux

- **Level:** Senior
- **Track:** Linux Systems Engineering / Kubernetes / Platform Engineering / SRE
- **Primary environment:** Ubuntu Server 24.04 LTS
- **Cluster bootstrap:** kubeadm
- **Container runtime:** containerd
- **Estimated completion time:** 100–150 hours
- **Lab model:** Multi-node Kubernetes cluster on Linux virtual machines
- **Cost:** Can be completed locally with VirtualBox, VMware, or another suitable hypervisor

- **Demonstrates:** Linux, Kubernetes, containers, networking, security, reliability.

> **2026 design note:** This project will not use the retired community Ingress-NGINX controller. Kubernetes retired Ingress-NGINX in March 2026, and the Kubernetes project now recommends Gateway API for new designs while the stable Ingress API remains available but frozen. Because the project scope explicitly includes **Ingress**, you will learn and implement the standard Kubernetes Ingress resource using a currently maintained controller, Traefik, and you will also understand where Gateway API fits into a modern design. # 03. Important Scope Boundary

You will build:

```text
1 control-plane node
2 worker nodes
1 administration node
```

This gives you **worker-node redundancy**.

It does **not** give you control-plane high availability.

Your cluster will contain:

```text
CP01
```

only.

Therefore, if CP01 is lost, the Kubernetes control plane becomes unavailable.

Existing workloads may continue operating temporarily on workers, but scheduling and control-plane operations are affected.

That limitation is deliberate.

Senior engineering means being accurate about what you built.

Do not describe this lab as:

> fully highly available Kubernetes.

It isn't.

Later you will document how a production design could extend this to multiple control-plane nodes.

# 19. Install containerd

Kubernetes talks to container runtimes through the Container Runtime Interface, or CRI. Current kubeadm documentation lists containerd as a supported runtime endpoint; Docker Engine itself does not implement CRI without an additional adapter. ([Kubernetes][2])

Install:

```bash
sudo apt update
sudo apt install -y containerd
```

Generate the default configuration:

```bash
sudo mkdir -p /etc/containerd
```

```bash
containerd config default |
sudo tee /etc/containerd/config.toml >/dev/null
```

Find:

```bash
grep -n SystemdCgroup /etc/containerd/config.toml
```

Configure containerd to use systemd cgroups in accordance with the runtime configuration appropriate to the installed containerd release.

Then:

```bash
sudo systemctl restart containerd
sudo systemctl enable containerd
```

Verify:

```bash
systemctl is-active containerd
```

and:

```bash
sudo ctr version
```

Do not proceed if containerd is unhealthy.

# 32. Understand Requests and Limits

This section:

```yaml
requests:
  cpu: "50m"
  memory: "64Mi"
```

tells Kubernetes what resources the workload requests for scheduling purposes.

This:

```yaml
limits:
  cpu: "250m"
  memory: "128Mi"
```

sets upper constraints.

Do not blindly copy production resource values from this lab.

These are intentionally small laboratory values.

Measure real applications before sizing production workloads.

---

# 33. Understand Readiness vs Liveness

## Readiness

Answers:

> Should this Pod currently receive Service traffic?

A failed readiness probe can remove the Pod from eligible endpoints without necessarily restarting it.

## Liveness

Answers:

> Does Kubernetes consider this container unhealthy enough to restart?

These solve different problems.

A common mistake is treating every application problem as a reason to restart the process.

# 37. Persistent Storage

Containers and Pods are disposable.

Application data often is not.

Kubernetes separates storage provisioning from storage consumption using:

```text
PersistentVolume
PersistentVolumeClaim
```

A PV represents storage available to the cluster. A PVC represents a workload's request for storage. PV lifecycle is independent of an individual Pod. ([Kubernetes][4])

For this local project, you will build a deliberately simple lab storage implementation and explicitly document its availability limitations.

---

# 38. Understand Local Storage Limitations

Kubernetes supports local PersistentVolumes, but local volumes remain dependent on the node containing the underlying storage. If that node becomes unhealthy, the volume can become unavailable to the workload. Kubernetes documentation explicitly warns that applications using local volumes must tolerate that reduced availability. ([Kubernetes][5])

Therefore:

```text
persistent
≠
highly available
```

This distinction will become one of your failure labs.

# 59. Build the Client Recovery Probe

Create:

```bash
nano scripts/application-probe.sh
```

Use the actual ingress endpoint for your lab:

```bash
#!/usr/bin/env bash

set -u

URL="${1:?Usage: $0 URL}"
INTERVAL="0.5"

while true; do

    timestamp="$(date -u '+%Y-%m-%dT%H:%M:%S.%3NZ')"

    code="$(
        curl \
            --silent \
            --output /dev/null \
            --write-out '%{http_code}' \
            --max-time 2 \
            "$URL" 2>/dev/null
    )"

    rc=$?

    if [[ "$rc" -eq 0 && "$code" =~ ^2 ]]; then
        printf '%s,SUCCESS,%s\n' "$timestamp" "$code"
    else
        printf '%s,FAILED,%s\n' "$timestamp" "${code:-NONE}"
    fi

    sleep "$INTERVAL"

done
```

Make executable:

```bash
chmod +x scripts/application-probe.sh
```

You will use this throughout failure engineering.

# 71. Understand Cordon vs Drain

## cordon

```bash
kubectl cordon worker01
```

means:

> Do not schedule new Pods here.

It does not automatically evict existing workloads.

## drain

Prepares the node for maintenance by evicting eligible workloads according to Kubernetes rules.

## uncordon

```bash
kubectl uncordon worker01
```

makes the node schedulable again.

This is operationally different from simply powering off a server.

# 94. Architecture Limitations

Create:

```bash
nano LIMITATIONS.md
```

Your final project should explicitly state at least:

```text
1. CP01 is a single control-plane node.

2. etcd therefore resides within a single-control-plane failure domain.

3. Local PV storage is node-dependent and is not HA storage.

4. All VMs may share one physical hypervisor.

5. The laboratory ingress exposure is not equivalent to a production cloud or datacenter load-balancing design.

6. The project does not claim that laboratory resource sizing represents production capacity.

7. The project does not implement production PKI lifecycle management.

8. The project does not implement a full cluster backup and disaster-recovery platform.

9. The project does not implement Kubernetes version upgrades.

10. The project does not claim application HA for stateful services merely because Kubernetes can restart Pods.
```

This is important.

You are not going to pretend Project 02 taught things it did not teach.
